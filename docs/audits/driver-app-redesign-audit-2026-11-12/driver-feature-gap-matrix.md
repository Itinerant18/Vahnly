# Driver App Feature Parity & Gap Matrix: DriveU vs. Vahanly vs. Redesign Plan

- **Audit Date:** 2026-11-12
- **Reference Target:** DriveU Partner Android Application (`com.driveu.partner` v11.24.28, versionCode 237)
- **Current Target:** Vahanly Driver Application (`client-app/`, `workers/api/`, `database/migrations/`)
- **Baseline Plan:** `DOC/DRIVER_APP_REDESIGN_PLAN.md` (2026-07-09)

---

## 1. Methodology & Parity Framework

This matrix establishes an evidence-based comparison between:
1. **DriveU Reference Evidence:** Verified capabilities extracted from reverse-engineered decompiled Hermes JavaScript (`DriveU_apk_for_rea/decompiled/hermes_decompiled.js`), native Java/Kotlin classes (`jadx_src/sources/com/driveu/partner/`), and API endpoint analyses (`DriveU_apk_for_rea/analysis/api_endpoints.txt`).
2. **Current Vahanly Implementation:** Concrete code inspected across `client-app/`, `workers/api/`, and `database/migrations/`.
3. **2026-07-09 Redesign Plan:** Proposed requirements from the existing plan.
4. **Scope Recommendation:**
   - **ADOPT:** Core category requirement essential for production operations in the rider-owns-car model.
   - **ADAPT:** Re-architect or re-implement using modern, privacy-preserving, or platform-appropriate patterns (e.g., Cloudflare Workers + Web Crypto instead of cleartext HTTP).
   - **DEFER:** Secondary feature suitable for post-launch phases (e.g., scratch cards, gamification).
   - **REJECT:** Inappropriate, anti-pattern, or non-applicable feature (e.g., cleartext network traffic, vehicle fleet registration in a driver-only service).

## 3. High-Value Discoveries from DriveU Research

### Discovery A: Duty Check-in Gating (Battery & Health Thresholds)
DriveU's Android application refuses to allow a driver to go on-duty if their battery is below 35% or network speed is below 50 kbps (`DriveU_apk_for_rea/config_constants.json`). This operational safeguard prevents drivers from going offline mid-trip due to dead phone batteries, which strands customer vehicles in the rider-owns-car model.
- **Vahanly Action:** Add battery level and connection sanity checks in `useDriverDutyStore` before firing the duty toggle API.

### Discovery B: Vehicle Condition & Odometer Verification Handoff
Unlike cab-hailing (where drivers use their own cars), in a driver-service app the driver is entrusted with a customer's personal vehicle. DriveU requires odometer readings, fuel percentage, and damage/scratch photo capture before trip start and at trip end to resolve billing and liability disputes.
- **Vahanly Action:** The Vahanly frontend already has UI fields for this (`startOdometer`, `startFuel`, `startOdoPhoto` in `DriverTerminalPage.tsx`), but the backend fails to store them. Vahanly must persist these fields into `orders` table upon `verify-otp` and `end`.

### Discovery C: Anti-Fraud and Mock Location Screening
DriveU incorporates native APK checks for mock location providers (`MockLocationEnableActivity`) and spoofing apps (`checkFraudApps`) to prevent drivers from faking GPS positions to collect minimum guarantee payments or cheat dispatch algorithms.
- **Vahanly Action:** Remove the development location spoofing tool (`client-app/src/components/DevLocationSpoof.tsx`) from production builds and implement server-side GPS teleportation filters in `CityDispatchDO`.

### Discovery D: Background Geolocation Persistence
DriveU maintains 4 dedicated native background services (`LocationPollerService`, `LocationUpdateService`, `CheckInForegroundService`) with `STICKY` notification channels. In contrast, Vahanly's driver app is built on web technologies where browser tabs throttle timers and pause GPS streaming when the device is locked or switched to Google Maps.
- **Vahanly Action:** Implement a native background geolocation bridge using Capacitor plugins (`@capacitor-community/background-geolocation`) to ensure continuous GPS telemetry streaming during active trips.
